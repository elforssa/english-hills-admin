## Owner direction and scope

English Hills is a reusable acquisition platform: multiple Meta Instant Forms, multiple landing-page forms and multiple campaigns/ads can run simultaneously. A campaign can reuse a form. Adding a campaign requires no application code change; adding a source within the supported field contract uses connection/form configuration and immutable mappings, not hardcoded IDs or a campaign branch in code. New canonical business semantics may require separate platform work; do not promise arbitrary integrations with no implementation.

Future Instant Forms enter EH intake/CRM directly. The Yearly Sheet → Apps Script → Zapier → Meta chain is legacy infrastructure and does not define future source onboarding. It may continue until intentionally retired. H3 prepares the reusable dormant destination and its current Instant Form matching contract; it does not choose the next campaign, channel or form. H4 evaluates actual source activation and proves no dual producer for that source/cohort. Completing a global legacy stop/drain investigation or designing permanent selective coexistence is not an H3 prerequisite.

The separate website direction is `landing page → EH durable intake → immediate CAPI Lead`, then later genuine CRM outcomes through a website-specific matching adapter over the shared lifecycle/outbox infrastructure. The owner describes immediate Lead as part of the previous marketing workflow; its external implementation was not inspected here. This repository's website endpoint does not currently send it.

## Later website outbound adapter boundary

Keep the shared CRM fact engine and delivery/outbox infrastructure. A later reviewed adapter supplies website matching and provider serialization, with source eligibility, immutable payload/event identity, privacy/stop handling and conservative receipt/retry behavior enforced at the existing boundaries. It must not masquerade website submissions as Meta Instant Forms or synthesize an original Meta `lead_id`.

The later contract must distinguish:

- **Immediate acquisition `Lead`:** derive its intent from a successful durable website receipt, not a button click, failed validation or eventual CRM qualification. Define atomic/recoverable enqueue, stable identity across client retries, delivery latency expectations, failure handling and any browser/server event deduplication contract. “Immediate” means prompt delivery after durable acceptance; it is not a guarantee that Meta has accepted the event when the intake response returns. Preserve intake success during provider outages.
- **Later CRM lifecycle outcomes:** consume actual committed CRM facts (for example Qualified/Converted) through the same lifecycle/outbox design. Define website-specific matching fields and consent/use/retention requirements; applicable browser/CAPI identifiers are candidates for later verification, not an approved payload. Source-specific SQL guards/contract support will need a separate reviewed extension, not a new CRM state machine.
- **Event separation:** website standard `Lead` is not the current custom CRM `Intake`, and neither implies a new approved sixth Instant Form lifecycle event. Decide any website Intake/acquisition relationship and browser/server identity rules in the later contract. Do not duplicate the immediate Lead through the current five-event adapter.

This is owner-directed future product scope, not implementation approval. No contact hashes, browser fields or website matching are added to the current `lead_id_only=true` contract. No website source must be selected for H3; launching one later requires its own readiness and authorization.
