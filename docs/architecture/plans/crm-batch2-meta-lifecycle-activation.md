### Revision 2 findings and evidence limits

**Funnel distinctions (M2/M3/M13–M15).** A technically accepted event is not proof of a recognized CRM integration. CRM source constants are necessary for recognition (M3); connection validation asks for at least one correctly formed event attributable to a lead (M14). Funnel-analysis validation separately requires a running campaign generating 200 leads/month and at least 60% lead coverage: the percentage of generated leads with matching uploaded events. Raw-lead upload is described as the best way to improve coverage, not as a separately enforced JSON field. M13’s waiting-stage checklist asks for seven days of data, sufficient generated-lead coverage and a minimum of two stages; three stages and sending all updates are best practices. Its example expects uploads matching every generated lead, while M14 supplies the explicit 60% threshold. Record this difference; do not turn either page into proof that two milestone names pass validation. M15 requires verified data before funnel configuration and actual stage ordering; optimization can target an earlier stage and Meta can adjust it. Daily uploads, 28-day conversion timing and conversion-rate guidance are optimization recommendations, not permission to change event truth, D2 eligibility or the seven-day upload-age limit.

Public evidence does **not** confirm that English Hills’ prospective, D2-eligible Qualified/Converted-only subset meets the relevant funnel or coverage requirements. Obtain an official clarification applicable to this use, plus account evidence of campaign volume, eligible-lead coverage and CRM status. Do not add raw leads/intermediate stages, disclose ineligible leads to improve coverage, manufacture predecessor events or equate two kinds with a qualified integration. Revision 1’s categorical “real scope incompatibility” is superseded by this narrower unresolved conclusion. Application/migration scope remains two kinds; expansion requires a separate owner-approved plan/ADR.

**Lossless lead ID (M7/M16).** `UserData` declares and sets `lead_id` as string (lines 46, 950–959) and `normalize()` passes it through unchanged (1284–1285). `ServerEvent.normalize()` copies that result; `EventRequest.execute()` builds `data` and invokes the Pixel events endpoint. The API/HTTP path passes the object without numeric conversion and serializes JSON. This is authoritative evidence of Meta’s supported SDK representation and sufficient to retain the current string contract; it is an inference about endpoint support, not an explicit endpoint wire-type guarantee or an account test. No new SDK dependency is proposed. Preserve canonical decimal text byte-for-byte, reject malformed IDs and add synthetic precision-boundary fixtures in the later implementation. Application/SQL type change: **no**. Owner approval of the overall contract is still required. If Meta later establishes numeric-only acceptance, stop: use a reviewed JSON serializer that emits validated decimal text as a raw integer token, never `Number`, with matching SQL/frozen-payload/hash validation and a forward migration. Do not implement that fallback without new evidence and approval.

**Deduplication (M4/M8).** Same event ID/name retains the first copy; M4 expressly supports batch retries and dropping previously stored duplicates. No inspected source establishes a numeric CRM server-only retention window. The browser/server 48-hour value cannot populate the required `deduplication_window_seconds`. Seven-day event age is not a dedup guarantee. Numeric horizon remains **UNRESOLVED**. Current-schema seeding remains blocked until the approved explicit hold-policy correction below is implemented and verified, alongside all remaining contract prerequisites.

### Approved owner retry/uncertainty decision — revision 3

**Owner:** repository owner. **Approval date:** 2026-09-30. **Scope:** activation plan revision 3, explicit no-uncertain-replay policy (revision 2 retry-horizon Option B). Source: the owner's follow-up instruction on PR #39, after initial head `e4bae3ca20f063b85cc00255335cd5a1bb4869ec`:

> I approve the no-uncertain-replay policy for CRM lifecycle delivery. Unknown or ambiguous provider outcomes must not be automatically resent unless authoritative provider evidence later establishes replay safety.

This is an accepted durable architecture decision, **not implemented**, not a provider guarantee and not H3/H4 approval. The owner also requires review holds, no silent uncertain resend during lease recovery, no director bypass and no invented numeric deduplication window. The policy is no longer pending; the exact future implementation still requires a separate task, CI, fresh independent review and release approval.

- Known safe/retryable pre-send failures may follow reviewed retry rules when durable evidence establishes that no request could have crossed the network boundary. Existing gates, repair requirements, backoff and bounds still apply; not every pre-send failure is automatically retryable.
- Once a request may have crossed that boundary, timeout, network error, ambiguous HTTP/body, unknown duplicate acknowledgment, response/finalization loss or an expired started-attempt lease is uncertain. Hold the delivery for review with no scheduled resend. An absent receipt or a later fixed credential does not prove non-acceptance.
- A retry after dispatch requires applicable authoritative evidence establishing non-acceptance or replay safety and a reviewed contract implementing it. General recovery advice, `is_transient`, HTTP 429/5xx, elapsed time or a director click are insufficient. There is currently no such uncertain-replay contract.
- Preserve original identity, name, destination, time, frozen matching payload and minimal terminal replay-prevention markers. Never move an uncertain delivery to a new identity, contract, destination or epoch to evade the hold. D7 remains a bounded eligible retry after repair, not an uncertainty override.
- A later verified guarantee is evidence for a separately reviewed contract/architecture update, not automatic permission to release held rows. Do not rewrite their frozen contract or revive terminal/expired/closed-epoch deliveries. Any later permitted replay must recheck safety at actual dispatch, including request timeout, and every existing eligibility, age, attempt, backoff and epoch bound.

Do not persist raw messages/errors. Missing/wrong count, `success` alone or malformed/ambiguous success is **unknown**, not sent or a reason to change identity.

M4 establishes duplicate suppression during retries but does not specify the exact HTTP/count/messages tuple for retrying a single already accepted event. A duplicate may be suppressed without a new effect; the inspected sources do not prove whether that retry returns `events_received=1`, zero or a special acknowledgment. Exact duplicate-response semantics remain **UNRESOLVED**; do not assume a distinct “duplicate” flag or that an HTTP success means a new conversion. M3’s older whole-batch rejection wording differs from M4’s newer partial-acceptance guidance; retain one event per request and never infer non-acceptance from an error on a multi-event batch. No provider test was sent.

## Rollback and recovery

**Exact shutdown order:**

1. Director/recovery operator calls `crm_disable_lifecycle` with fresh connection version, closing the epoch and disabling the destination. Verify both states. This blocks new claims/begin checks without waiting for a Vercel deployment.
2. DB operator sets only `crm-lifecycle-primary` inactive and verifies it. Stop any separately approved manual/backup trigger as well. Do not touch `crm-intake-primary`.
3. Vercel operator sets lifecycle live gate false and verifies the new Production deployment is READY on the correct alias. Existing requests may already have crossed the gate; changing environment is not instantaneous revocation.
4. If exposure/compromise requires, revoke the dedicated outbound Meta token. Preserve inbound credentials. Account for already-started requests as possible effects; do not mark them unsent merely because a switch changed.
5. Preserve delivery/attempt/audit history and safe incident evidence. Inventory pending/sending/unknown rows without payload export, reconcile uncertainty under the verified provider contract, and let approved terminal/retention handling run through a separately authorized safe maintenance path if cron remains paused. Paused scheduling also pauses automatic cleanup; record a bounded maintenance owner/deadline.

If step 1 is inaccessible, immediately pause cron and close server gate, revoke outbound token if warranted, and close the DB epoch as soon as access returns. Record reduced containment rather than claiming all effects stopped. None of these steps recalls accepted events.

Recovery uses a reviewed fix, CI and fresh independent re-review of the new SHA; explicit new prospective activation approval, a new epoch, current policy and verified READY gate precede cron-last restart. Never reopen an epoch, reset attempts, mutate a frozen identity/payload, replay old mock/sent/dead/suppressed rows or carry disabled-period milestones forward. A single director retry is allowed only for an eligible row within the same open epoch after repair and all existing checks, including the approved no-uncertain-replay hold; neither director action nor lease recovery may bypass uncertainty. It is not general incident replay permission. No destructive migration rollback.
