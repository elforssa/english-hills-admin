# Owner summary

## What will change

Outcome 3 replaces the receptionist CRM presentation with one admissions operating workspace: Opportunities with Board/List, system Views, a contextual lead drawer, and Tasks/My Work. Admissions Calendar projects existing placement bookings and center-visit tasks. English Hills remains the system of record; an opportunity is the existing `crm_leads` row, not a new entity.

## What staff/users will be able to do

Find a parent and the correct learner/program opportunity; see the next action; explicitly record calls and WhatsApp conversations; qualify, book/reschedule placement, close with a reason, reopen and start enrollment without losing workspace context. Dragging proposes an existing business action; it never changes a status by itself. My Work shows assigned work across overdue, today, tomorrow and upcoming buckets.

## What remains restricted

No arbitrary status changes, manual conversion, new confirmation authority, campaign/ad disclosure to reception, financial analytics, integrations or HR access. No Meta activation, credential work, Production mutation or application implementation is authorized by this architecture PR. Placement cancellation is not supported by the existing model and is excluded from the recommended v1; owner acceptance of that limit is required.

## UI impact

GoHighLevel-inspired operating patterns, Linear-like visual restraint and existing English Hills branding: compact cards, restrained colors, fast search, reusable right drawers, clear next actions and keyboard-accessible contextual actions. This is a purpose-built language-center workspace, not a CRM builder. Existing French UI vocabulary remains; the English names below identify product concepts, not a requirement to translate the application to English.

## Database impact

Propose six additive, bounded RPC reads for Opportunities, filter options, operational acquisition summary, task buckets, calendar and cursor-based timeline; reuse existing tables, authorization predicates and operational projections. No new business tables, write commands, backfill, policy edits, enrollment/finance triggers or provider changes. Additive forward read-model migrations are expected across the two implementation batches, with narrowly justified indexes after synthetic query-plan evidence. No migration file is created by this task.

## Important security decisions

Keep the current operational roles and director-only technical boundary. My Leads and My Work are filters, not new ownership authorization. Campaign/ad fields remain absent from receptionist payloads, including counts/filter facets and form answers. Reuse protected enrollment and placement commands without broadening permissions. Keep CRM tables inaccessible to ordinary browser CRUD.

## Risks / owner review points

Architecture PR: **Tier 2**, substantial product/read-model design with unchanged sensitive boundaries. The proposed read/presentation implementation is Tier 2; a change to RLS, authority, sensitive existing writes, finance, conversion or provider behavior escalates the affected scope to Tier 3 before implementation. Actual Production migration operations remain Tier 3. Approve the precise v1 cancellation/calendar/acquisition limits below before implementation; this document is a proposal, not evidence of release.

### Opportunities and system Views

One title, “Admissions Pipeline,” one fixed stage set: NEW, CONTACTING, ENGAGED, QUALIFIED, CONVERTED. CONVERTED is a terminal display column, not an active follow-up status; never add it to the existing `ACTIVE` constant. LOST and NOT_QUALIFIED appear in Closed, not board columns. No manual ordering field: cards sort by created time descending and ID descending within stage, consistently with List. Next-task urgency remains visible and is the focus of Tasks.

**Common filter algebra:** authorized, nonmerged opportunities → selected system View → text/contact/owner/source/program filters → optional List status or Board column. Every count uses the same predicates before pagination. All filters combine with AND. Unknown View/filter/cursor values fail validation rather than broadening a query. Textual source/program values are exact-match bounded inputs (maximum 200 characters), never patterns or SQL fragments. All Leads means all seven statuses; on Board show five columns plus a visible filtered Closed count/link. Explain “Board shows open and converted opportunities”; total matches may exceed column totals by the Closed count. Switching to List reveals the same full match set. Closed forces List and disables Board with a clear explanation; returning to another View restores the previous layout.

Server evaluates dates at `Africa/Casablanca` with one returned `as_of` per response. D0 is today's local midnight, D1 tomorrow's, D2 the following midnight, each separately converted to an instant (never add a fixed 24 hours across offset changes).

| System View / stable key | Exact predicate before user filters |
| --- | --- |
| All Leads / `all` | All nonmerged leads, including converted and closures; default View. |
| My Leads / `mine` | `owner_id = auth.uid()`, all statuses. Unassigned excluded. Explicit other-owner filter yields zero, never silently replaces this predicate. |
| New Today / `new_today` | `created_at >= D0 AND created_at < D1`, all statuses. Means created today, not currently NEW; subsequent calls do not make a lead disappear from this View. |
| Needs Attention / `attention` | Active NEW/CONTACTING/ENGAGED/QUALIFIED meeting any current 083 Today condition: earliest open task overdue (`due_at < as_of`); NEW with open first_contact; earliest task in [D0,D1); no open task and no future planned linked placement; or CONTACTING stale by its immutable policy's `stale_contacting_minutes` using `coalesce(last_attempt_at,created_at)`. Preserve 083 priority 1–5 for labels, not a new scheduling rule. |
| Follow Up Today / `follow_up_today` | Active lead with at least one open task of any existing CRM task type in [D0,D1). Includes earlier-today overdue tasks; excludes previous days' overdue work and placement bookings without a task. |
| Placement Tests / `placement` | Active lead with any linked `Planifié` placement (including past appointments awaiting resolution), or open `confirm_placement_test` / `post_test_followup` task. Completed test alone does not keep it in this work View. Historical tests remain in drawer/admissions. |
| Qualified / `qualified` | `status = QUALIFIED`, regardless of qualification step or linked pre-enrollment. |
| No Response / `no_response` | Active lead with `crm_security.failed_count(lead) > 0` in its current outreach cycle. Includes ENGAGED/QUALIFIED with subsequent unanswered outreach; wrong number and WhatsApp do not qualify. No automatic closure at five. |
| Closed / `closed` | `status IN (LOST,NOT_QUALIFIED)`; reason/status/date visible. CONVERTED stays in All Leads/board, not this View. |

Owner filter: all / me / unassigned / explicit staff UUID. Source filter uses first submission `channel` (`manual`, `meta_instant_form`, `website`), optionally exact `source_label`, never latest touch or inferred Meta campaign. Program filter uses exact nonempty `session_type`, or exact `program_interest_text` when session is absent; provide “Not specified” for both absent. Preserve case/value identity and label which kind of program value a facet represents; do not guess a program from an arbitrary answer. Text search reuses current 120-character bounded contact/learner substring and canonical/partial-phone semantics. No searching notes, provider identifiers or form answers. Preserve explicit contact filter for sibling navigation. No saved-view tables, filter JSON language or customizable columns.

### Semantic interactions and truthfulness

Dragging is an action shortcut with an accessible menu equivalent. Show valid targets and the proposed action before opening the dialog. The card remains at the server-confirmed stage while the dialog is open/pending; cancel is a no-op. No optimistic persistent stage movement, success before confirmation, drag-only functions, backward mutation or generic `setLeadStatus`. There is **no Undo** for calls, qualification, closure, reopen or enrollment: these create audited facts/tasks and may create lifecycle eligibility; Undo cannot erase them. A later supported action is separately explicit and audited.

| Source → target/action | Supported flow and existing command | Required evidence / resulting behavior |
| --- | --- | --- |
| NEW → CONTACTING | Open call-outcome dialog; `crm_record_call_outcome` | Actually completed call, explicitly choose no_answer/busy/declined/unreachable. Only backend failure record moves NEW to CONTACTING. Never preselect a fabricated failure to satisfy the drop. Other chosen outcomes follow their actual semantics. |
| NEW/CONTACTING → ENGAGED | Open meaningful-conversation dialog; phone callback decision via `crm_record_conversation_decision`; WhatsApp via `crm_record_whatsapp`; in-person via `crm_record_conversation` | Channel, evidence note and next action. Phone wrapper callback requires callback; generic phone conversation can use `crm_record_call_outcome` with spoke_with_contact and next task. Do not feed WhatsApp/in-person through phone-only wrapper. Backend records conversation and resets outreach. |
| NEW/CONTACTING/ENGAGED → QUALIFIED | Qualification dialog; `crm_qualify_lead`, or phone wrapper decision=qualify after an actual phone conversation | Existing conversation evidence or explicit new channel+note; step placement_test/center_visit/enrollment/other and matching future task; other requires explanation. Direct NEW→QUALIFIED may record real conversation atomically; do not manufacture an earlier separate call. |
| QUALIFIED → CONVERTED | Focus existing enrollment if linked, otherwise `CrmEnrollmentDialog` → `crm_start_enrollment` | Explicit learner candidate review, enrollment selection or supported new Submitted/Trial intent. Remains QUALIFIED until trusted Confirmed/Validated; existing confirmed linked candidate may convert through command. No “Convert Lead” button. |
| NEW/CONTACTING/ENGAGED → CONVERTED | Unsupported drop; focus explanation/qualification action | Must qualify before starting enrollment. No automatic qualify or silent chain of mutations. |
| Any active → Lost / Not Qualified contextual action | `crm_close_lost` / `crm_close_not_qualified` | Explicit supported reason; note mandatory for other. No permanent closure board column. Optional closure action menu, not an invisible drop target. |
| LOST/NOT_QUALIFIED → reopen contextual action | `crm_reopen_lead` | Reason + explicit future task. Backend chooses ENGAGED if conversation history exists, otherwise CONTACTING; new outreach cycle. Cannot drag to a chosen stage. |
| Same-stage drop | No-op | Does not reorder persistently or write activity. |
| Any backwards move; CONVERTED → any stage; closures → arbitrary stage | Unsupported | No new status setter, reopen Converted or compensating mutation. |

All writes retain lead version and relevant task version; placement edits use expected_updated_at; enrollment retains candidate-review and enrollment version guards. `40001`: refetch detail and affected lists/counts, preserve explanatory input where safe, require renewed explicit confirmation with latest evidence. Never auto-replay stale business intent. Unknown network result: preserve the same request UUID and exact payload for retry; changed payload gets a new UUID. Permission/validation errors show safe messages, not raw SQL/provider data. On success invalidate Board/List counts/pages, Tasks, Calendar, detail, placements and timeline; reconcile the confirmed returned state. If filter membership changes, announce why the card left the view. Discard late responses for obsolete filters and key caches by user/role plus all filters/cursors.

**Call:** visible action opens a compact panel with phone/copy/device `tel:` and separately “Record outcome.” Opening the panel or device handler writes nothing. Support exactly no answer, busy, declined, unreachable, spoke with contact, wrong number. In-person conversation gets an explicit action in the same dialog family. Wrong number does not advance attempt count and requires a next action; do not count it as Unreachable. No caller, telephony integration or delivery inference.

**WhatsApp:** `wa.me` launch only; separately “Mark WhatsApp sent” (`whatsapp_sent`, activity only) and “Record meaningful WhatsApp conversation” (`meaningful_whatsapp_conversation`, evidence + next action). Opening the external app never records sent. No Conversations module or WhatsApp API.

**No-answer:** display server current-cycle failures and scheduled next call. When two failures have been recorded, say “2 of 5 failed calls recorded”; for a next task with ordinal 2, “Next attempt: 2 of 5.” After five, say “Automatic call sequence finished”; explicit extra calls remain possible and the actual count may exceed five. The backend alone assigns ordinals and follows Day 1 twice / Day 2 / Day 4 / Day 6 anchored to the first actual failure, with configured Casablanca windows/minimum gap. No frontend cadence algorithm or assumed live policy hours. Missing policy produces actionable error; staff cannot fix policy from this workspace.

**Closures:** Lost reasons are `unreachable`, `not_interested`, `price`, `schedule`, `location`, `chose_competitor`, `postponed`, `other`; NQ reasons are `age_not_suitable`, `program_not_suitable`, `invalid_spam`, `duplicate`, `outside_scope`, `other`. Unreachable requires at least five current-cycle failures and CONTACTING/ENGAGED/QUALIFIED; other genuinely known reasons may close earlier. The fifth call only stops the automatic sequence. Closure is explicit; reopening is audited and never erases earlier closure.

**Conversion/payment:** `enrollment != payment != conversion != collected revenue`. Show enrollment and CRM state separately. No new payment projection in v1; authorized staff may open existing receipt/student operations for actual payment state. Do not show “unpaid” merely because payment data was not fetched. Starting enrollment is not confirming it. Receptionist cannot freely Confirm/Validate; existing trusted financial/authorized enrollment effects remain. Conversion downgrade review remains director-only as returned by the existing detail RPC; no new exposure of that flag.

### Tasks / My Work

Reuse `crm_tasks`, existing command dialogs and Today predicates. The workspace is task-centric, one row per open task on an active nonmerged lead, not one row per lead. Default assignee is me (`assigned_to = auth.uid()`); offer All staff, specific staff and Unassigned. Lead-owner filter is independent and combines with assignee using AND. No implicit fallback from unassigned task to lead owner. Changing lead owner does not reassign existing tasks; show that warning. Extend reassignment UI to use existing `crm_reassign` task_id/expected_task_version/assigned_to for an explicitly selected task, never silently bulk-transfer tasks.

Mutually exclusive server buckets: OVERDUE `due_at < as_of`; TODAY `as_of <= due_at < D1`; TOMORROW `[D1,D2)`; UPCOMING `>= D2`. Thus overdue includes earlier today. Each bucket has its own count and cursor sorted due_at ascending, ID ascending. Include all eight existing types: first_contact, contact_attempt, callback, whatsapp_followup, confirm_placement_test, post_test_followup, center_visit, enrollment_followup. Keep dates server-derived across Casablanca offset transitions. Refresh visible time-dependent data every 60 seconds and on focus; no background browser scheduling of tasks.

Keep a separate Needs Attention link/summary for taskless prospects and exhausted call sequences; never synthesize task rows for them. Intake review is separately bounded. Actual planned placement bookings appear in Calendar and optional linked Today agenda, not fake tasks. Completing call tasks routes to call outcomes; other completion/cancellation keeps existing next-action validation. Routine engine tasks continue unchanged; staff scheduling/rescheduling remains supported where already authorized.

### Admissions Calendar and placement limits

Deliver a coherent date/week agenda in v1, not a duration/availability scheduler. Project `placement_tests` (CRM-linked and currently authorized unlinked tests) and open `center_visit` CRM tasks on active nonmerged leads. Planned appointments show even if their linked lead has closed or converted, with its stage, because closure does not cancel a real test. Default placement state is Planifié; optional “Include completed tests” includes the other three existing states. Canceled/completed tasks are omitted. Stable event key `(kind,id)` prevents duplicates; preparation/result-follow-up tasks are not duplicate placement bookings. No callbacks, academic lessons or unscheduled enrollment states masquerading as appointments. No existing consultation/trial appointment model was found: exclude those categories rather than invent dates from Trial enrollment or group timetable.

Placement start = date_test + valid heure interpreted in Casablanca. Legacy unlinked records with missing/invalid time appear in a “Time unspecified” day lane, never guessed midnight; CRM-linked commands already require valid time. `examinateur` is a display string, not verified staff identity: no examiner availability/staff filtering/assignment claim. No duration exists for tests; render a point/agenda entry. Center visits use due_at and scheduled_end_at only where genuinely present; do not invent a standard end. No calendar drag-reschedule in v1. Click linked placement/visit → same lead drawer and existing action; unlinked test → existing PlacementTestModal. Bound any supporting modal option queries; calendar must not fetch entire student/group lists merely to render appointments.

Booking from qualified drawer reuses `crm_book_placement_test`, including confirmation-task versions, unique planned booking and learner linkage. Rescheduling/result editing reuses `crm_update_placement_test`; refresh all projections. Qualification step “placement_test” only prepares work; it does not book a test. Result milestone makes post-test work, never converts.

**Cancellation gap:** no `Annulé` state, cancellation event or guarded cancellation command exists. Do not show a functioning Cancel booking control, delete a linked record, mark it Passé, clear its time, or cancel only its preparation task and claim the appointment is canceled. ## Bounded backend contract

The six new reads below are proposed API names to implement only after approval. Keep existing public RPC signatures compatible. No materialized view or cache table is needed. Private helpers may factor common predicates but have no API grants; never accept SQL fragments, arbitrary filter JSON or dynamic sort expressions.

| Proposed read | Fixed inputs and bounded output |
| --- | --- |
| `crm_get_opportunities` | Typed View enum key, query <=120 chars, optional contact UUID; typed owner mode/UUID, first-channel/source-label, program kind/value; layout board/list; optional validated stage; limit default 25 max 25, validated cursor. Initial Board returns counts for all seven statuses and <=25 cards for each of five columns; subsequent stage request returns only that column page. List returns <=25 rows and same filtered counts. Shared private predicate drives all paths. |
| `crm_get_opportunity_filter_options` | One validated facet kind source/program, bounded label search <=120, cursor, limit <=50. Returns distinct authorized first-source or program values with explicit kind. Staff selector reuses `crm_list_staff`; fixed channel/status choices need no discovery query. Never fetch technical attribution to build facets. |
| `crm_get_operational_acquisition_summary(p_lead uuid)` | One required, non-null lead UUID; return null for a missing lead, otherwise exactly `first_inquiry` and `latest_inquiry`, each with exactly `channel`, `source_label`, `occurred_at` from the lead's first/latest submission links. At most two fixed objects, no pagination or submission IDs. Explicit server-side field construction from CRM lead/submission facts; never return or merge a broad detail/attribution object. Same minimal shape for every permitted operational role. |
| `crm_get_work_queue` | Validated bucket, assignee mode/UUID, optional lead-owner filter, limit default 25 max 50, cursor. Returns bucket counts, selected task page, lead card summary, task version/assignee/ordinal and authoritative as_of/timezone/boundaries. One request for active bucket; inactive buckets lazy-load. |
| `crm_get_admissions_calendar` | Start/end local dates, exclusive end, maximum 42 days; kind all/placement/center_visit; include-completed boolean; cursor and limit default 100 max 100. Returns typed events and continuation, not full tables or technical JSON. Range required, no unbounded all-time mode. Events expose kind/id, lead/student IDs where already authorized, display name, stage, placement status or task type, local date/time, valid start/end if known, examiner label or task assignee, and edit concurrency token; no notes, scores, full student/profile or financial records. |
| `crm_get_timeline` | Lead UUID, before cursor, limit default 20 max 50. Fixed operational history fields equivalent to `crm_get_history`, descending occurred_at/ID, has_more/next_cursor; no raw details/source_key/attribution payload. Preserve old history RPC. |

Every new public read validates stored actor role through `crm_security.require_reader(false)` before data access, fixes search_path to pg_catalog/pg_temp, uses fully qualified relations and stable read-only statements, revokes inherited PUBLIC/anon/authenticated/service_role execute before granting authenticated only. Helpers remain private. Projections never exceed current operational field/row authority. These are new entrypoints to existing rights, not a change to role policy. Any need to widen current authority is a Tier-3 stop. Validate unlinked placement row access against cumulative placement RLS (including 077/083/096) and role tests before accepting the calendar implementation; don't rely on a broad reader helper to invent access for another role.

Card projection reuses `operational_card` field meanings but builds a compact explicit object after paging IDs; do not inherit its full nested placement notes into every card. Add safe owner display name from existing staff projection semantics, created_at for cursor, closure reason/date for List, and task ordinal/assignee from existing task fields. No full profile rows. Keep detail 084 behavior intact. The first/latest acquisition block lazily calls only `crm_get_operational_acquisition_summary`; it does not reuse the broad `crm_get_lead_detail` response. No proposed new write RPC is necessary.

Cursor contract: deterministic immutable `(created_at,id)` descending for opportunities, `(due_at,id)` ascending for tasks, `(local_date,time-or-unspecified,kind,id)` ascending for calendar and `(occurred_at,id)` descending for timeline. Cursor envelope includes version, kind/stage, ordering tuple and normalized filter fingerprint; validate types/length <=2KB and reject mismatched filters. Fingerprint is consistency metadata, never authorization; all predicates/role checks are re-evaluated server-side. No long-lived snapshot promise across requests. Concurrent membership/due-time changes may require refresh; deduplicate by stable ID and reset affected pages after successful mutation. Counts and initial pages come from one SQL statement snapshot. Subsequent page response supplies refreshed counts/as_of; no claiming exact consistency between independently cached responses.

Bound output: first Board <=125 cards, per-column <=25 by default; no background auto-drain of cursors. List/Tasks use page or load-more with retained DOM cap; Calendar shows load-more/truncation explicitly and must not imply a partially loaded range is complete. Server counts aggregate matching IDs without rendering card JSON or joining every activity. UI never downloads the entire lead table to group locally. Counts may scan matching rows server-side, but execution must meet the measured budget below.

Existing useful indexes: 078 status/owner/created/ID, contact, open-task assignee/due/ID, open-task lead/due/ID, activity lead/time/ID and attempt uniqueness; 083 linked placement date and one-planned-test uniqueness; 091 terminal-task covering index. These do not automatically optimize status-without-owner or substring search. Measure candidates such as nonmerged `(status,created_at DESC,id DESC)`, global `(created_at DESC,id DESC)`, planned-test `(date_test,id)` and exact program/source predicates only if EXPLAIN establishes need. Do not unconditionally add a broad GIN index, extension, policy or all conceivable indexes. Index names/definitions and migration filename are implementation evidence to record, not preallocated numbers here. Preserve unique/integrity indexes.

Performance acceptance on disposable synthetic local Supabase: at least 10k opportunities, 50k tasks, long activity history and >100 calendar entries, with skewed stages, siblings and all Views. Run EXPLAIN (ANALYZE, BUFFERS), including nested statements; record hardware, fixture size, cold/warm timings and query plans. Proposed interactive budget: warm p95 <=500ms per RPC over 20 representative calls, first Board <=1s end-to-end on local browser, no read >2s on that fixture. A budget miss blocks read-model handoff until optimized or explicitly reassessed with owner evidence; never solve it by silently returning partial counts or dropping predicates. This is a target, not a measured result of this docs task.
