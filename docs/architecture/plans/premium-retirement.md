# Owner summary

**Premium retirement.** Premium is a cancelled product. This plan removes the Standard/Premium "Formule" and the whole Premium workshops/homework module from the platform, so every Yearly student is simply a Yearly student.

## What will change

- The word "Formule" (and "Standard"/"Premium" as a formule) disappears from the receipt form, receipt list, print page, PDF, receipt e-mail, finance export, student form, student list and student page, and reports.
- The Premium workshops module is removed: the "Heures Premium" page and menu entry, workshop groups, memberships, attendance, homework, the Premium tabs and panels in the teacher, parent and student portals, the Premium block in the timetable and student page, and the Premium section of the Academic Operations report.
- All existing Premium students become ordinary students; their Premium dates are cleared.
- New Yearly receipts store "Yearly · 2026/2027" (no formule word) as their description, **including every later instalment paid on a non-legacy Yearly charge created before the change** (the new receipt text is built from session type and school year, not copied from the old charge text; a payment on a legacy balance keeps its own "Reçu historique …" text). Per your instruction on the review, the plan also removes the plan word from the stored description of **open, non-voided Yearly charges** (not issued receipts) in a separately approved, counted, rehearsed data step.
- The database tables, rules and uploaded homework files that only served the module are deleted in a **second, separately approved release**, after a full export is kept.

## What staff/users will be able to do

- Create receipts, charges and students exactly as before, minus the formule choice. Numbering, payments, balances, enrollment and conversion do not change.
- Nothing new is added. Teachers, parents and students lose the homework and workshop screens.

## What remains restricted

- Roles, RLS, finance authority and the trusted conversion boundary are unchanged. Receipts and charges remain read-only for browser users.
- No security rule is loosened to make the removal pass. The only permission changes are removals: the four receptionist workshop commands, the receptionist read policies on the workshop tables, and the homework upload purpose.

## UI impact

- One page route and one menu item are removed. Formule fields, filters, badges and PDF/e-mail rows are removed. Several panels and report sections are removed with no replacement (see Design D6). The Premium badge next to student names in the student list is removed too.
- An old receipt reprinted later no longer shows a Formule line. Its stored description text (for example "Yearly · Premium · 2026/2027") still appears wherever that text is displayed; you decided (Q1) to leave it untouched. Open charges are cleaned by the data step; new receipts never contain it.

## Database impact

- Release A: one forward migration (provisionally 113) that changes only the receipt/charge creation function. No table is dropped. A separately approved text-only data step then cleans the plan word out of open Yearly charges (reversible from an export).
- Release B: one destructive forward migration (provisionally 114) that drops five tables, their functions, triggers and policies, two storage-registry columns, and two student date columns. It refuses to run unless no Premium student remains.
- A separate, owner-approved Production data step moves existing Premium students to Standard. Production counts are not read by this task; they are listed as pre-release checks.

## Important security decisions

- Storage-registry functions that gate every upload and download (student photos, portfolios, enrollment documents) must be redefined to remove the homework branch. This is the highest-risk part of Release B and is tested against the existing upload flows.
- The destructive migration uses no `DROP … CASCADE`, so a dependent view, foreign key or policy on another table makes it fail instead of being silently removed. That does **not** catch references inside function bodies (they are not tracked as dependencies), so the migration is also followed by a catalog scan of every function body, policy, view, trigger and constraint for any remaining Premium reference, and it refuses to run while any homework file still exists in storage.
- Production SQL and file deletion are never run automatically; each needs explicit release approval.

## Risks / owner review points

1. **Q1 (decided 2026-10-08):** after the new-receipt fix and the open-charge cleanup, issued Yearly receipts and settled or voided non-legacy Yearly charges still contain "Standard"/"Premium" in their stored text. You decided to leave them untouched: no text rewrite and no display-time handling.
2. **Q7 (decided 2026-10-08):** a payment whose response was lost before the change and retried afterwards returns the original receipt, not a second one, because migration 113 keeps accepting the old request fingerprint (Option A).
3. Homework files and workshop history are permanently deleted in Release B. Rollback after that is only from the export or a database backup.
4. Moving students to Standard fires an existing database trigger that ends their workshop memberships. The export must exist first.
5. Future-dated workshops, memberships and pending homework (counts unknown) will be discarded. You must see these counts before approving Release B.
6. Teachers, receptionists, parents and students who open a removed address are redirected to their own home screen; only admin/director see "page not found" (existing role-allowlist behavior).

# Design

## D1 — Finance contract (Release A, migration 113)

`create_charge_payment_financial` is recreated from the **096** definition (never an earlier snapshot) with the minimum change:

- The `plan_type` payload key is **accepted and ignored**. A stale browser tab or an old build sending `Standard` or `Premium` during rollout can neither fail nor create a Premium record. This also makes the order migration-first safe: the old client keeps working with the new function; the new client would fail against the old one.
- For a Yearly charge, `plan_type` is written as the fixed value `'Standard'` (required by `charges_yearly_formula_check`; the constraint is not changed). Non-Yearly stays NULL.
- `service_description` of a **new Yearly charge** becomes `concat_ws(' · ', 'Yearly', <school year>)`, that is `Yearly · 2026/2027`. Other sessions and the "Autre" form are unchanged.
- **The description of every new receipt on a non-legacy Yearly charge is built by the function, not copied from the charge text (owner instruction on the PR #118 review, Part B).** Today the function copies `v_charge.service_description` and `v_charge.plan_type` into the receipt, so an instalment paid on a charge created before 113 (for example `Yearly · Premium · 2026/2027`, plan `Premium`) would create a new receipt that still says Premium. In 113 the receipt's `service_description` is built as `concat_ws(' · ', 'Yearly', v_charge.school_year)` **only for non-legacy Yearly charges** (`v_charge.session_type = 'Yearly' and not v_charge.legacy`; just `Yearly` if such a charge has no school year). **A legacy charge keeps copying its own text.** Legacy charges (migrations 055/056) store `Reçu historique <receipt number>`, carry no plan word and no school year, and paying a legacy balance is a supported flow (the 096 wrapper's `v_charge.legacy` branch, `scripts/README-enrollment-workflow.md`, the `legacy_balance` case in `test-receipt-charge-payments.sql`); building `Yearly · <year>` for them would invent a school year and destroy the historical reference. Every other session type also keeps the charge's text (built only from session type, "Autre" detail and year, never a plan word; a test asserts it). The receipt's `school_year_snapshot`, amounts and snapshots are unchanged.
- The receipt row **always** stores `plan_type = NULL` (the column is already nullable): the function must not copy `v_charge.plan_type`, because pre-113 charges hold `Standard` or `Premium`. New receipts therefore carry no formule in the table, the e-mail Edge Function (which omits the row when empty) or any future consumer.
- The function body must not contain the word Premium (comments included): the post-114 catalog scan and the absence guard treat any occurrence as a failure.
- **Retrying an already-committed request after 113 (lost-response recovery) — Option A, decided by the owner (Q7, 2026-10-08).** Facts verified in 096: every committed request leaves a row in `financial_requests` keyed by the idempotency key with a SHA-256 fingerprint of the normalized request; a retry of the same key from the same actor returns the original `charge_id`/`receipt_id` with `replayed: true` only if the recomputed fingerprint is identical, otherwise it raises `Idempotency key conflict: request contents changed.` Nothing in the repository (migrations, jobs, code) deletes `financial_requests` rows, so committed keys stay replayable indefinitely; whether Production has ever purged them is **NEEDS VERIFICATION** (R0 read-only count of rows by age). The fingerprint contains `plan_type` **only for a request that creates a new Yearly charge** (the field is omitted when `charge_id` is supplied and nulled for non-Yearly sessions), so only a lost-response retry of a *first Yearly payment or commitment* committed under 112 is affected; instalments on an existing charge (including a zero-payment request on an existing charge) and non-Yearly charges keep their fingerprint, whereas a zero-payment Yearly commitment that creates a new charge is affected exactly like a first payment (the fingerprint includes `plan_type` whenever there is no `charge_id` and the session is Yearly, regardless of the amount). Simply dropping `plan_type` from the fingerprint would make that retry fail with the conflict error at any later time, not only during one in-flight submit. **Option A (decided):** 113 recomputes the fingerprint exactly as 112 did: for a request with no `charge_id` and session `Yearly`, the `plan_type` value *supplied in the payload*, normalized by **the same expression 112 used (096 line 539): `nullif(btrim(p_payload->>'plan_type'),'')`**, is included in the fingerprint input under the key `plan_type` only when there is no `charge_id` and the session is Yearly (and is absent, as a null stripped by `jsonb_strip_nulls`, when the key is absent or blank), so the fingerprint is byte-identical to 112's for every request 112 could have committed (those could only carry the two historical values; anything else was rejected before commit); it is never stored, never validated and never used for charge or receipt data. A new client sends no `plan_type`, so its fingerprint omits it. Result: a retry of any request committed under 112, by an old build still open in a browser tab, returns the original receipt (`replayed: true`), with no second receipt and no new number. Cost: a vestigial read of one payload key kept for replay compatibility (documented in the function comment without using the retired word, and removable only if the owner later confirms the old keys are purged). **Option B (not chosen):** keep the simpler fingerprint and rely on a staff procedure (see Q7). Both options keep the safe failure for any other mismatch, and the client shows the French wording defined in Q7 instead of the raw English message.
- Unchanged: numbering, amounts, discount and balance rules, idempotency table, events, e-mail opt-in, ACLs (`revoke all … from public,anon,authenticated,service_role` on the inner command; grant on the public wrapper). The public wrapper `create_charge_payment` needs no redefinition unless the implementer finds it passes `plan_type` explicitly (check against the local 112 database with `pg_get_functiondef`).

Client side: `buildServiceDescription` drops the `planType` parameter; `receiptServiceSummary` no longer appends the plan; `receiptInitialCharge` and `ReceiptForm` stop holding `plan_type`; the Formule selector, preview word, receipts-list PREMIUM badge, print "Formule" row, PDF row and details entry, and finance export column are deleted. The Edge Function drops its "Formule" row and `formula` variable and is redeployed (a Production operation for the release task).

5. **Constraints and columns:** drop `storage_asset_bindings.premium_submission_id` (and its unique index), recreate `storage_asset_bindings_check` over the remaining four columns; drop `storage_assets.premium_session_id`; recreate `storage_assets_purpose_check` without `'premium_homework'`; recreate `notifications_type_check` without it.
6. **Tables:** `premium_attendance`, `premium_homework_submissions`, `premium_sessions`, `premium_group_memberships`, `premium_groups`, in dependency order, each `DROP TABLE` without `CASCADE`. Their policies, indexes, restrictive receptionist deny policies and table triggers go with them.
7. **Functions:** the ten workshop functions and four receptionist commands listed in the table above, by exact signature.
8. **Students:** drop `premium_start_date`, `premium_end_date` and `students_premium_dates_check`; replace `students_plan_type_check` with `plan_type = 'Standard'` (valid because the guard proved no other value remains). This prevents a direct API write from re-creating a Premium student. `charges`/`receipts` constraints still permit the historical value, because issued history is not rewritten (Q1) and those tables are read-only to browser roles.
9. **Final in-migration catalog assertion**, then `notify pgrst, 'reload schema';` The assertion and the identical read-only release-verification query scan, across every schema other than `pg_catalog`, `information_schema` and `pg_toast*`: `pg_proc.prosrc` (all function bodies, including `storage_security`, `operational_security`, `crm_security` and any other private schema), `pg_policies` (`qual`, `with_check`), `pg_views`/`pg_matviews` definitions, `pg_get_triggerdef` of every trigger, `pg_get_constraintdef` of every constraint, and column defaults, for the case-insensitive token `premium`. Zero matches are allowed except exactly three named constraints that deliberately retain the historical value: the `plan_type` check on `charges`, `charges_yearly_formula_check`, and `receipts_plan_type_check`. In the migration a failure raises and rolls the whole transaction back; the same query is rehearsed locally and run read-only after Production application.

What "no `CASCADE`" does and does not do: without it, dropping a table fails if a view, a foreign key from another table or a policy on another table depends on it, so those are never removed silently. PostgreSQL does **not** track references inside function bodies, so a function that mentions a dropped table would drop fine and fail at run time; that gap is what the catalog scan closes.

`plan_type` columns on `students`, `charges` and `receipts` and the list-RPC `p_plan` parameter remain (Q2, option A). They are inert: nothing reads them for display and nothing can set them to anything but the fixed value. Their existence and the reason are documented in PRODUCT_RULES at implementation.

## D5 — Production data step (existing Premium students)

A reviewed, idempotent script committed under `supabase/manual/` (the existing pattern, like `drop_photo_consent.sql`), executed only on explicit release approval, after Release A is verified and the export exists. Intent:

```
update public.students
   set plan_type = 'Standard', premium_start_date = null, premium_end_date = null
 where plan_type = 'Premium' or premium_start_date is not null or premium_end_date is not null;
```

- **Pre-checks (owner-authorized read-only, release task):** counts of Premium students (by status, deleted, session type), students with Premium dates but Standard plan, active/future/historic memberships, active groups, future-dated sessions, sessions with attendance, homework by status and with files, `storage_assets` and `storage.objects` counts/bytes for `premium_homework`, `notifications` of the type (sent/unsent), receipts/charges holding `Premium` or `Standard` in `plan_type` or `service_description` (for Q1), split into open non-voided Yearly charges (the D5a target), settled or voided charges, and issued receipts. Counts only are written into the release record; no names or contact data are copied into the repository.
- **Side effects the owner must expect:** the 054 trigger ends/deletes the moved students' workshop memberships; `updated_at` is bumped (a staff member with an open student drawer would get the existing stale-edit message once).
- **Idempotency:** the `where` clause matches nothing on a second run. Report `rows affected` before/after and re-run the count query to prove zero.
- **Mandatory before-change restore export (the D5 step must not run without it).** Immediately before the step, the release task exports, keyed by student id, every student the step will change: `id`, original `plan_type`, `premium_start_date`, `premium_end_date`, `updated_at`, `deleted_at`, `status` and `session_type` (context), **plus every `premium_group_memberships` row of those students** with all its columns (ids, group, dates, `active`). It is kept in owner-controlled private storage, never in the repository, PR, logs or chat; the release record holds only the row counts and a SHA-256 checksum of each file. This restore set is distinct from, and taken after, the B0 whole-table export. The script enforces it fail-closed: it requires the operator to declare `premium_retirement.export_rows` and `premium_retirement.export_sha256` as session settings and raises if either is missing or if the declared row count differs from the number of students it is about to change.
- **Restore script and rehearsal.** A reviewed `supabase/manual/premium_students_restore.sql` (committed beside the step) reads the export format and restores, in this order, the students' `plan_type` and both dates, then the deleted or deactivated membership rows with their original ids (students first, because the membership guard validates against the student's entitlement). Before the Production step is approved, the implementation PR must show a **local restore rehearsal on a synthetic database** (wired into the Release B CI rehearsal): seed Premium students with dates and active, future-dated and historic memberships, take the export, run the step (the 054 trigger deletes or ends memberships), run the restore, and assert plan, dates and every membership row (id, group, dates, `active`) equal the export; `updated_at` is compared only for information because triggers bump it. Row counts and checksum handling are exercised too (a wrong declared count makes the step raise).
- **Rollback:** run the restore script from that export. Valid only **before** Release B (after 114 the Premium value is rejected by the tightened check and the tables are gone; recovery is then only the database backup/export).
- **Placement:** a separate step, not inside either migration (Q4 below), because a migration also runs on fresh local and CI databases where it would be a no-op, and Production data corrections should not be coupled to the schema ledger.

## D7 — Storage handling for homework files

Homework files are objects in the `documents` bucket (`assets/<uuid>`), tracked by `storage_assets`/`storage_asset_bindings`.
