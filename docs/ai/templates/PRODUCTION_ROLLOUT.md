# Production rollout / operator task

Inputs: reviewed PR, exact approved head SHA, owner release approval with scope, migration manifest, deployment target, rollout order and recovery owner. Read [AGENTS](../../../AGENTS.md), approved plan and implementation/review evidence. Production mutation/activation is Tier 3 under the [risk-tier policy](../../../AGENTS.md#risk-based-lifecycle), even if the originating change was lower risk. Use a separate release task/agent. Reuse implementation/CI evidence where applicable; verify deployment-state checks here.

**Explicit human release approval is required before any Production mutation**, including merge that triggers Vercel, migrations, credentials/configuration or provider activation. Architecture approval is insufficient. Prepare the concrete release checklist before requesting missing approval.

1. Confirm PR/head SHA, independent review of that SHA, CI/preview/local upgrade checks and no intervening changes. Verify current main, deployed source, migration ledger and recovery readiness. Stop on drift.
2. State merge strategy (repository-approved merge/squash/rebase), expected source commit relationship and application/database compatibility. Follow the approved ordering: migration-first only with explicit compatibility/access-window approval; otherwise deploy disabled compatible code first. Never infer order from this checklist alone.
3. Merge only the approved revision. Wait for Vercel **Production READY** and verify its exact source commit, target/alias and configuration. A READY preview or an old READY deployment does not suffice. Stop on failure; do not continue activation.
4. Apply only explicitly reviewed forward migrations in the approved order. Verify ledger version, name and schema/function effects. If normalization is needed, stop and prepare a separately approved ledger repair backed by applied-SQL evidence; never blindly mark a migration applied, rerun deployed SQL or rename history to hide a mismatch.
5. Run approved Production acceptance, role/security probes, finance/conversion checks relevant to scope, integration/scheduler health and runtime-error inspection. Use authorized fixtures, reversible probes and bounded data; never copy customer payloads into reports. Confirm no other-role or inbound-integration regression.
6. Stop on deployment failure, migration mismatch, unexpected security behavior or health regression. Follow the approved recovery plan: disable new external effects first; a UI rollback does not revoke database permissions or undo sent events. Preserve financial/audit/delivery history. Database repair uses reviewed forward migrations; destructive rollback requires separate approval.
7. Close out only after acceptance: record PR/head/merge/deployed SHA, migrations/ledger, verification date, evidence source and limitations in CURRENT_STATE and relevant architecture/security/workflow/ADR docs. Mark the plan COMPLETED, move it to `docs/architecture/plans/completed/`, repair links and update FEATURE_INDEX. Report remaining issues honestly. Documentation closeout is its own reviewable change, not automatic permission for another Production deployment.
