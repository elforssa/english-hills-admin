# Implementation task

Inputs: risk tier/rationale (Markdown-only policy/security changes are not automatically Tier 1), approved scope, plan path/revision and recorded owner decisions when architecture is required, current main and dedicated implementation branch. Follow the [risk-tier policy](../../../AGENTS.md#risk-based-lifecycle); Tier 3 requires a separate task/agent from architecture.

Read [AGENTS](../../../AGENTS.md), the approved plan including its IMPLEMENTATION CONTRACT when applicable, and referenced ADR/product/security/workflow docs directly from the repository. Use the recorded revision and approval evidence rather than requiring the owner to relay the plan through another GPT conversation. Verify current main and reconcile intervening code/migrations before implementation. Missing required approval or a widened product/security boundary requires an owner decision; ordinary implementation/test failures within the contract should be fixed autonomously.

Implement only approved scope. Use local Supabase, synthetic fixtures and external email disabled. Use forward migrations only: never edit deployed migrations (001–097 at this template's creation; confirm the latest deployment inventory). Do not use Production secrets/data. Add appropriate positive, negative, regression, concurrency and browser tests for the changed behavior. Preserve finance/conversion invariants and other-role denials.

While developing, run focused relevant tests for changed areas. Inspect actual behavior and authorization, not merely green output. Run focused local checks and any explicitly required local validation, then commit/push and open/update the PR before waiting for required CI for the current revision. Passing CI satisfies overlapping complete-suite checks; extra local full runs are needed only for explicit contract requirements, missing coverage, environment-specific behavior or doubtful evidence. Markdown-only changes use the documentation checks in AGENTS and existing required CI still applies. Revalidate failures or later changes as needed. Update implementation-status docs accurately with evidence, keeping implemented, merged, deployed and Production-verified separate. Update ADRs/product/security/workflows only when their durable facts change.

Follow the [internal QA policy](../../../AGENTS.md#internal-implementation-qa): inspect your final diff and perform one focused internal self-check to catch obvious mistakes, verify changed risk areas and confirm test/documentation accuracy. Cover security, authorization, migrations, data integrity, concurrency, external providers, retry/error handling and regression risk as applicable. For small Tier 1 changes, the final diff inspection is this focused check. Fix findings and target re-checks at affected behavior and safeguards; broaden only if architecture, security boundaries, database models or material risk change. Do not repeat cycles just because a prior review occurred.

Even detailed self-review or internal subagent review is implementation QA: it does not approve the PR, count as independent review, authorize merge or replace a required reviewer. Never label internal checks “approved” or issue READY FOR FINAL REVIEW / CHANGES REQUIRED as your own independent-review verdict. Reuse evidence rather than duplicate separate release/operator checks unless needed to prove correctness.

Stage explicit paths only; never `git add .` or `git add -A`. Inspect the staged diff, commit/push and open a PR. Do not merge or deploy Production. For Tier 2 and Tier 3, a fresh independent reviewer is mandatory and examines the exact PR head SHA. If that reviewer finds defects, the original implementer fixes them on the same branch/PR, runs focused tests and one targeted internal re-check of the changed areas, then commits/pushes the new SHA and waits for required CI. Obtain fresh independent re-review of that exact SHA; the same reviewer may continue if independent of implementation, and a new agent/session per fix is not required. Do not reuse approval for old code. Tier 1 needs no mandatory independent reviewer unless scope grows; reassess its tier before continuing.

Return branch, exact head SHA, PR number/link, risk tier/rationale, approved plan revision (if applicable), migration filenames (if applicable), tests/checks completed with results and evidence tied to the current revision (head/base SHA, tested merge SHA for synthetic-merge CI, run links and local tested SHA/tree as applicable), internal QA completed, documentation updates and remaining blockers. Identify any unresolved owner decision. Follow the [handoff policy](../../../AGENTS.md#implementation-handoff) and report exactly one status appropriate to the tier:

- **Tier 1: IMPLEMENTATION INCOMPLETE** if approved scope, relevant checks/required CI, internal QA or the open PR is incomplete, or implementation handoff blockers remain.
- **Tier 1: IMPLEMENTATION COMPLETE** when approved scope, relevant checks/required CI and internal QA are complete for the exact current head SHA, the PR is open and no implementation handoff blockers remain. Independent review is optional unless scope grows or the owner requests it.
- **Tier 2/3: NOT READY FOR INDEPENDENT REVIEW** if implementation, required checks, internal QA or the open PR is incomplete, evidence is failed/missing/stale, or handoff blockers remain.
- **Tier 2/3: READY FOR INDEPENDENT REVIEW** when implementation is complete for the current scope, the exact current head SHA is identified, all required tests/checks pass for that SHA, internal QA is complete, the PR is open and no handoff blockers remain. A separate independent reviewer is mandatory.

Report and preserve any merge/release hold separately. Implementation completion is not PR approval, merge authorization or release authorization.
