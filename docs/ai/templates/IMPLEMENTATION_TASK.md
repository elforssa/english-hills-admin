# Implementation task

Inputs: risk tier/rationale (Markdown-only policy/security changes are not automatically Tier 1), approved scope, plan path/revision and recorded owner decisions when architecture is required, current main and dedicated implementation branch. Follow the [risk-tier policy](../../../AGENTS.md#risk-based-lifecycle); Tier 3 requires a separate task/agent from architecture.

Read [AGENTS](../../../AGENTS.md), the approved plan including its IMPLEMENTATION CONTRACT when applicable, and referenced ADR/product/security/workflow docs directly from the repository. Use the recorded revision and approval evidence rather than requiring the owner to relay the plan through another GPT conversation. Verify current main and reconcile intervening code/migrations before implementation. Missing required approval or a widened product/security boundary requires an owner decision; ordinary implementation/test failures within the contract should be fixed autonomously.

Implement only approved scope. Use local Supabase, synthetic fixtures and external email disabled. Use forward migrations only: never edit deployed migrations (001–097 at this template's creation; confirm the latest deployment inventory). Do not use Production secrets/data. Add appropriate positive, negative, regression, concurrency and browser tests for the changed behavior. Preserve finance/conversion invariants and other-role denials.

While developing, run focused relevant tests for changed areas. Inspect actual behavior and authorization, not merely green output. Run focused local checks and any explicitly required local validation, then commit/push and open/update the PR and confirm remote CI was successfully scheduled for the current revision. Stop polling at that point; do not repeatedly query GitHub or narrate unchanged status. Passing CI satisfies overlapping complete-suite checks; extra local full runs are needed only for explicit contract requirements, missing coverage, environment-specific behavior or doubtful evidence. Markdown-only changes use the documentation checks in AGENTS and existing required CI still applies. Revalidate failures or later changes as needed. Update implementation-status docs accurately with evidence, keeping implemented, merged, deployed and Production-verified separate. Update ADRs/product/security/workflows only when their durable facts change.

Follow the [author self-check policy](../../../AGENTS.md#author-self-check-before-handoff): inspect your final diff and perform one focused author self-check to catch obvious mistakes, verify changed risk areas and confirm test/documentation accuracy. Cover security, authorization, migrations, data integrity, concurrency, external providers, retry/error handling and regression risk as applicable. For small Tier 1 changes, the final diff inspection is this focused check. Fix findings and target re-checks at affected behavior and safeguards; broaden only if architecture, security boundaries, database models or material risk change. Do not repeat cycles just because a prior review occurred.

Do **not** spawn an internal reviewer, independent-review or re-review subagent from the implementation task. The focused author self-check is the only pre-handoff review-like activity. It does not approve the PR, count as independent review, authorize merge or replace the required reviewer. Never label it “approved” or issue READY FOR FINAL REVIEW / CHANGES REQUIRED from implementation. Reuse evidence rather than duplicate separate release/operator checks unless needed to prove correctness.

Stage explicit paths only; never `git add .` or `git add -A`. Inspect the staged diff, commit/push and open a PR. Do not merge or deploy Production. For Tier 2 and Tier 3, a fresh independent reviewer is mandatory and examines the exact PR head SHA. After confirmed CI scheduling, **stop the implementation task**. If CI is running, return **AUTHOR WORK COMPLETE — REMOTE CI PENDING** with exact head SHA and CI run reference/status. The coordinator verifies the terminal exact-SHA CI result later and launches the separate reviewer task/session only after required CI succeeds; do not continue into formal review yourself. If that reviewer finds defects, the original implementer fixes them on the same branch/PR, runs focused tests and one targeted internal re-check of the changed areas, then commits/pushes the new SHA, confirms CI scheduling and hands off without polling. The coordinator verifies terminal successful required CI before re-review. Obtain fresh independent re-review of that exact SHA; the same reviewer may continue if independent of implementation, and a new agent/session per fix is not required. Do not reuse approval for old code. Tier 1 needs no mandatory independent reviewer unless scope grows; reassess its tier before continuing.

Return branch, exact head SHA, PR number/link, risk tier/rationale, approved plan revision (if applicable), migration filenames (if applicable), tests/checks completed with results and evidence tied to the current revision (head/base SHA, tested merge SHA for synthetic-merge CI, run links and local tested SHA/tree as applicable), author self-check completed, documentation updates and remaining blockers. Identify any unresolved owner decision. Follow the [handoff policy](../../../AGENTS.md#implementation-handoff) and report exactly one status appropriate to the tier (or the scheduled-CI pending status):

- **AUTHOR WORK COMPLETE — REMOTE CI PENDING** when implementation, focused/local checks, one self-check, commit/push, PR creation and confirmed CI scheduling are complete but required CI is still running. Include exact head SHA and CI run reference/status; the coordinator verifies terminal results later. This is not READY FOR INDEPENDENT REVIEW.
- **Tier 1: IMPLEMENTATION INCOMPLETE** if approved scope, relevant checks/required CI, author self-check or the open PR is incomplete, or implementation handoff blockers remain.
- **Tier 1: IMPLEMENTATION COMPLETE** when approved scope, relevant checks/required CI and author self-check are complete for the exact current head SHA, the PR is open and no implementation handoff blockers remain. Independent review is optional unless scope grows or the owner requests it.
- **Tier 2/3: NOT READY FOR INDEPENDENT REVIEW** if implementation, required checks, author self-check or the open PR is incomplete, evidence is failed/missing/stale, or handoff blockers remain.
- **Tier 2/3: READY FOR INDEPENDENT REVIEW** when implementation is complete for the current scope, the exact current head SHA is identified, all required tests/checks pass for that SHA, author self-check is complete, the PR is open and no handoff blockers remain. A separate independent reviewer is mandatory.

Report and preserve any merge/release hold separately. Implementation completion is not PR approval, merge authorization or release authorization.

Risk tier and test selection are separate; follow [CI selection and remote-CI handoff](../../../AGENTS.md#ci-selection-and-remote-ci-handoff). A Tier-3 Meta/security document may use safe docs-only CI and still require independent review. Code/database/security behavior changes receive appropriate full tests. v1 routes only safe `docs/**/*.md` changes to lightweight documentation checks; everything else retains full CI. READY FOR INDEPENDENT REVIEW requires terminal successful required CI, not merely scheduling.
