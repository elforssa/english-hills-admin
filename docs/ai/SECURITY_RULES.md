# Security and permission boundaries

## Adopted S1 credential security boundary — 2026-10-05

[S1 invariants](../architecture/plans/crm-meta-lifecycle-credential-simplification.md#permanent-security-invariants), owner-adopted through PR #93 / main `284c2fe32014f8f3011ac6677ddfe99b0a16ca22`, retain dedicated C2/Employee/dataset, least privilege across capability/tier/tasks/scopes/effective authority, no DQA, human-only handling and Vercel Production-only sensitive custody. The sole active [Gate-B credential runbook](../architecture/plans/crm-h3-s1-gate-b-credential-runbook.md) uses one final token and one bounded supported diagnostic validation, plus safe revocation/replacement. No token value enters AI, source, logs, screenshots or intermediate persistent storage; runtime resolves only the server secret reference.

Credential/activation evidence lives in [CURRENT_STATE](CURRENT_STATE.md) and the [Gate-B closeout](../architecture/evidence/crm-h3-s1-gate-b-closeout-2026-10-05.md). Gate B requires focused independent contract review and explicit credential/Production operational authority. Gate C still requires separate final live review/owner approval. H3-06/07/08 remain outside the credential runbook. Historical Rev7 procedures are retired; [original security chronology](../architecture/history/security-rules-before-outcome-1.md) preserves their approval scope. No security boundary is changed by this navigation cleanup.

In the advisory implementation, deferred pending-stop retrieval is director-only through `crm_list_pending_lifecycle_stops`; anonymous/service API execution and all other roles are denied, and direct marker/audit table access stays closed. Responses contain only opaque CRM scope IDs and coarse intent/reason/time, never request/actor details, proof answers, provider matching IDs or contact values. Trusted resolution must commit actual later-source safety stops under its preheld exclusive identity barrier, and unhanded pending acquisition exclusions cannot start an audit-erasure clock. See the [findings remediation evidence](../architecture/evidence/crm-r4-advisory-implementation-2026-10-01.md#independent-review-findings-remediation--2026-10-01).

Authorization is not sidebar visibility. UI, page route, server/API/RPC and RLS/database must agree. Middleware skips API role gating so each handler must authenticate itself. The middleware matcher exempts only static assets, image optimization, the same-origin Sentry tunnel (`/monitoring`) and Vercel's `/_vercel/` platform prefix (Speed Insights); application routes, including look-alike paths, stay gated and [middleware tests](../../scripts/test-middleware-security.mjs) prove it. Real-user monitoring events are stripped of query, fragment and record IDs in both URL and route in the browser ([filter](../../src/lib/rumScrub.mjs)), and the reporter passes an explicitly scrubbed route; the real beacon is checked by the owner after deployment. Database role is authoritative; client input and editable Auth metadata are not role proof. Never broaden RLS or remove checks/tests merely to make frontend access work.

## H3-02 transport boundary

The [approved H3 multipart contract](../architecture/plans/crm-h3-technical-readiness.md#authentication-compatibility-and-proof) adds the dedicated outbound token only to the transient multipart form immediately before HTTP. Frozen payloads, query strings, persisted data, logs and error output must remain token-free; no simultaneous bearer authentication or manually supplied multipart boundary is permitted. Fixed Graph host/path, redirect rejection, no-store, eight-second timeout, bounded response handling and no uncertain replay remain. H3-02 changes no ACL, RLS, privacy or sharing-stop boundary and provisions no credential. [Implementation evidence](../architecture/evidence/crm-h3-02-implementation-2026-10-02.md); current release evidence is in [CURRENT_STATE](CURRENT_STATE.md).

Group membership derives from enrollments; the learner-file group is database-maintained (live: migration 120 on 2026-10-25, migration 121 on 2026-10-26; [EGC-r2](../architecture/plans/enrollment-group-consistency.md), [ADR-010](../architecture/decisions/ADR-010-group-membership-from-enrollments.md)). Placement and removal keep the existing `assign_group` capability (director, admin, receptionist); **Ancien apprenant** and reopening are director/admin; the year close, the archived list and restore are director-only; exceeding capacity is director/admin with a logged reason. Guard triggers refuse, for every role, direct writes of the file group, of a placed learner's programme/level, of a status that contradicts the enrollments and of enrollment history; the M2 checks (active enrollments have a group, a programme and a year; ended rows have their shape) are validated constraints. Stale or duplicate refusals raise `PT409` (ADR-009). The new commands are executable by `authenticated` only (not `anon`, not `service_role`). The clean-up log (`maintenance` schema) has no API access.

The [Production-verified O3-r2 Batch-1 reads](../architecture/evidence/outcome-3-batch-1-implementation-2026-10-05.md) reuse operational role checks. ## Sensitive data and privileged code

- Batch E release E-2 ([plan PCR-r2](../architecture/plans/payment-corrections-receipts.md), migration 122; implemented on a branch, not merged or deployed): the desk limits above (discount reason and 10 % reception cap, payment-date window, 10 % reception confirmation threshold) are enforced in the payment functions with the stored role. `get_finance_review_queue` is director-only. Discount reasons live in `charge_discount_reasons` (written only by the definer payment function; SELECT under the same staff rules as `charges` staff and reception reads; no family, teacher or `anon` access, no API write), not on `charges`, which families can read. Receipt numbers cannot be supplied or changed and receipts cannot be hard-deleted or truncated by any role, `service_role` included; the two exceptions (historical numbering D1, local test clean-up) need a transaction-local setting and a session user that is a member of `postgres`, which no API request has. `receipt_number_counters` and the `finance_security` schema have no API privilege. Voids take the shared enrollment-intent lock (`PT409` when a CRM linkage holds it). Release E-1 switched payslip creation off (`POST /api/admin/payroll` answers 409) until the accountant validates the payroll rules.
- Financial and payroll-sensitive data require explicit authorization. [043](../../supabase/migrations/043_teacher_sensitive_data_isolation.sql) isolates full teacher/compensation rows to admin/director; non-HR consumers use a fixed teacher directory projection. [Payroll API](../../src/app/api/admin/payroll/route.js) checks stored admin/director role before privileged computation/write; [065](../../supabase/migrations/065_payroll_direct_write_guard.sql) blocks client payroll writes.
- CRM tables are not ordinary client CRUD surfaces: use authorized read models/commands. SECURITY DEFINER code needs explicit actor/role validation, fixed search paths and restricted execute grants. Service-role access is not a substitute for checking the caller.
- Keep secrets/tokens/private credentials out of repository, browser bundles, logs and documentation. [Service-role client](../../src/lib/supabase-admin.js) is server-only. Secret references may be documented; secret values must not be.
- Meta lifecycle feedback must never send child name, child DOB, child age, level, placement-test data, internal notes/history, task history, finance/payment data or arbitrary form answers. Revision-4 live scope remains original Meta lead ID only plus the fixed nonpersonal CRM source constants; hashed adult email/phone remain mock legacy behavior and are forbidden in live payloads. Migrations 101–102 add closed five-kind maps, policy-appropriate D2 evaluation for every kind, immutable prospective producer boundary/ownership controls, chronological attempt fencing and irreversible unknown markers while reusing the existing outbox. Their public tables use RLS with direct API grants revoked; worker and director RPCs remain narrow and receptionist controls remain denied. The later advisory-D2 amendment preserves actual stops and existing required policies. Code presence is not permission to activate; H3/H4 approval remains mandatory. [CURRENT_STATE](CURRENT_STATE.md) owns seeded-contract and dormant-deployment evidence.
- Meta Insights (migration 114): the ad-account token exists only as a Vercel Production Secret under a `CRM_META_INSIGHTS_TOKEN_*` reference read at request time; the database, diagnostics, reports and UI carry only the reference name. Configuration, requests, retries, diagnostics and the cohort report are director-only (`require_reader(true)`); claim, finish, fail and `crm_enqueue_insights_refresh` are service-role only; no API role may execute `crm_security.invoke_crm_insights_scheduler`, which accepts only the exact Production URL. `/api/cron/crm-insights` authenticates its own dedicated bearer and does no live work unless `CRM_META_INSIGHTS_LIVE_ENABLED=true`; the worker re-checks that gate before resolving the secret. [Contract](../crm-meta-insights.md#live-synchronisation-dgi-a-migration-114).
- Lead campaign attribution (migration 115, DGI-B B1; released 2026-10-11/12, switch enabled 2026-10-12): the hierarchy is resolved from data already in the database by `crm_security.resolve_meta_hierarchy`, which has no API grant; writes go only through the service-role sweep `crm_enrich_meta_attribution` and the service-role finalizer, both guarded by the unchanged `crm_security.protect_attribution` trigger (NULL fields only, redacted rows never touched); the director switch `attribution_enrichment` and its database-set `started_at` are the only configuration; `crm_save_meta_connection`, `crm_get_meta_diagnostics` and `crm_get_marketing_cohort` stay `require_reader(true)` with `authenticated` execute only. No token is read, no provider call is made, no PII enters the two new columns, the diagnostics or the scheduler response. [Contract](../crm-meta-insights.md#lead-campaign-attribution-dgi-b-b1-migration-115).
- Protect Meta webhook raw-body signature verification, public intake validation/rate limiting/origin policy, internal worker authentication and the separate scheduler bearer. Origin/CORS alone is not authentication. [Integration runbook](../crm-operations-runbook.md).
- Untrusted JSON bodies are capped before parsing ([readBoundedJson](../../src/lib/boundedJson.mjs): 32 KB for `/api/public/inscription`, 1 MB for `/api/email/send`, 32 KB for the website inquiry), and validation failures on those routes return a fixed message, never the validation issue list. The anonymous inscription schema is strict: unknown keys, including `documents_urls`, are refused.
- Website inquiry limiter key: Vercel overwrites client address headers, so behind the website proxy the CRM sees the proxy's egress IP. A visitor IP is accepted only from the HMAC-signed `x-eh-visitor-token` header (`CRM_WEBSITE_PROXY_SECRET`, bound to `request_key`, ±300 s). Verification must stay total and fail-safe: any defect falls back to the egress-IP key (with a site/form/reason-only warning when a header was present), never skips the limiter, never 503s and never logs the header or IP; the header is never CORS-allowed. Only the HMAC pseudonym is stored. [Contract](../crm-website-inquiries.md#visitor-key-header).
- Policy expressions ([ADR-013](../architecture/decisions/ADR-013-policies-once-per-statement-keyset-reads.md); migration 124 on a branch, not merged or deployed):
  - call `get_my_role()`, `get_my_teacher_id()`, `get_my_email()` and `auth.uid()` only as `( SELECT f() AS f)`;
  - put a single-role per-row helper (for example `teacher_can_access_student_group`) behind that role's wrapped test.

  A rewrite keeps every policy's name, table, command, roles and kind, and is proven equivalent before/after for every identity (read, write and function outputs; `scripts/test-speed-as-the-centre-grows-local.mjs`). Read models that only shape rows the caller may read (`list_activity_log`, `report_*`, `search_students_page`) are SECURITY INVOKER and executable by `authenticated` only. A failed profile or Auth read is never treated as "no profile" or "signed out": middleware answers 503 and the browser shows a retry screen, with no role.
- Preserve storage authorization, PII scrubbing and immutable audit/financial evidence. Never export real customer data into local fixtures without explicit authorization.

## Production boundary

Production migrations, provider activation, secrets, scheduler and Vercel configuration require explicit approval. Never automatically push linked migrations or mutate production to verify documentation. Deployed migrations are immutable and new migrations must first pass local verification. [AGENTS](../../AGENTS.md) is the execution policy; [CURRENT_STATE](CURRENT_STATE.md) records the limits of deployment evidence.

## Dependency audit gates

Production dependency advisories at moderate or above remain CI-blocking without exceptions.
